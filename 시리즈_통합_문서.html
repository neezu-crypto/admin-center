스트리머 시리즈 통합 문서

여러 저장소·여러 게임이 하나의 Firebase 프로젝트를 공유하는 구조 — 코드만 봐서는 알기 어려운 부분을 기록한다
저장소 5개 공유 Firebase 프로젝트 soop-stock-market 1개 공유 오리진 neezu-crypto.github.io
01

이 문서가 존재하는 이유

이 시리즈는 게임마다 별도 저장소로 존재하지만, 인증·재화·관리 세션은 하나의 Firebase 프로젝트(soop-stock-market)를 여러 저장소가 함께 씀으로써 연결된다. 이 "공유"는 각 저장소의 코드만 따로 읽어서는 잘 드러나지 않고, 두 저장소를 동시에 봐야만 이해되는 경우가 많다.

이 문서의 목적 — 게임 기획(무엇을 만드는가)이 아니라, 저장소 사이의 연결 방식(어떻게 공유되는가)을 기록한다. 각 게임 고유 기획은 그 저장소의 자체 기획서 문서를 본다.

Functions 코드베이스가 여러 개인 이유 — 한 Firebase 프로젝트에 여러 저장소가 각자 firebase deploy를 실행하는 구조라, 이름이 우연히 겹치면 서로 덮어쓸 위험이 있다. presetgallery·admincenter처럼 격리된 코드베이스 이름을 쓰는 저장소는 그 위험을 피하려는 것. 배팅시장·주식시장은 아직 default 코드베이스를 그대로 쓰고 있어 이름 충돌 방지가 순전히 "안 겹치게 짓기"에 의존하는 상태 — 게임이 더 늘어나면 이것도 격리하는 걸 고려할 것.
03

로그인 세션 자동 공유

배팅시장·주식시장·배경시장·통합 관리 센터에 각각 로그인해야 할 것 같지만, 실제로는 한 곳에서 로그인하면 나머지도 처음 방문 시 이미 로그인된 상태로 시작한다.

전제 조건 두 가지가 모두 맞아야 함: 1) 같은 오리진(scheme+host+port) → 전부 https://neezu-crypto.github.io (경로만 다름, CNAME 커스텀 도메인 없음) → 브라우저 저장소(IndexedDB)는 경로가 아니라 오리진 단위로만 분리됨 2) 같은 Firebase apiKey → Auth 세션은 firebase:authUser:{apiKey}:{앱이름} 키로 저장됨 → apiKey가 다르면 오리진이 같아도 완전히 별도 세션이 만들어짐
실제로 있었던 문제 — 주식시장의 프론트엔드(index.html)만 자기 고유 Web App의 다른 apiKey를 쓰고 있어서, 나머지 3곳과 오리진은 같은데도 세션이 안 섞였다. 주식시장의 apiKey를 나머지와 동일하게 맞추고 나서야 공유되기 시작했다. appId는 이 메커니즘과 무관(저장 키에 안 들어감) — interior-3d-viewer의 appId는 원래부터 배팅시장과 달랐지만 세션 공유엔 문제없었다.

즉 새 페이지/저장소를 이 시리즈에 편입시키려면, firebaseConfig의 apiKey를 반드시 기존 값과 동일하게 맞춰야 한다 — Firebase 콘솔에서 새 Web App을 등록해도 발급된 apiKey를 그대로 쓰면 안 되고, 기존 apiKey로 바꿔 써야 세션이 공유된다.

04

인증 스트리머 상태가 3곳에 걸쳐 있는 이유

uid(로그인 세션)는 위 방식으로 공유되지만, "이 uid가 인증 스트리머인가"를 판단하는 방식은 앱마다 다르다 — 그래서 uid 공유만으로는 인증 상태까지 자동으로 안 따라온다.

데이터주체내용
streamerVerifications공유 노드(두 앱이 같이 씀)SOOP 아이디를 canonical key로 삼는 인증 원장. 배팅시장은 이걸 uid로 직접 조회해서 판단
users/{uid}/streamerVerified주식시장 전용주식시장은 이 자체 캐시 플래그로 판단(공유 노드를 직접 안 봄) — "계정 보호" 등 자산 관련 특전의 기준
bettingMarket/profiles/{uid}배팅시장 전용인증 승인 시 채워지는 닉네임/SOOP아이디/아바타 — 안 채워지면 프로필이 초기 상태로 보임
실제로 있었던 문제 (3건 연쇄)
  • 매칭 키 비대칭 — 배팅시장은 SOOP 아이디로, 주식시장은 닉네임으로만 기존 레코드를 찾아서, 같은 사람이 두 앱에서 각각 인증받으면 uid가 다른 중복 레코드 두 개가 생겼다. → 양쪽 다 "SOOP 아이디 우선, 닉네임 폴백"으로 통일
  • 해제 비대칭 — 배팅시장의 인증 해제가 streamerVerifications만 지우고 users/{uid}/streamerVerified는 안 건드려서, 해제해도 주식시장에선 계속 "보호된 계정"으로 남았다. → 승인/해제 양쪽 함수가 서로의 플래그도 같이 정리하도록 수정
  • 프로필 비대칭 — 주식시장에서 인증해도 배팅시장 프로필은 안 채워져서, 배팅시장에 처음 들어가면 초기 상태로 보였다. → 주식시장의 승인 함수가 배팅시장 프로필도 같이 채우도록 수정
신규 uid 초기화 함정 — 주식시장의 users/{uid}는 "노드가 존재하면 이미 초기화된 계정"으로 취급해 시작 자금(1,000,000원)을 안 준다. 그래서 배팅시장 쪽에서 이 uid의 플래그를 미리 써넣을 때는 노드가 아직 없으면 시작 자금까지 같이 채워서 만들어야 한다(그냥 플래그 하나만 쓰면 나중에 실제 접속했을 때 돈을 못 받는 사고가 남).

06

통합 관리 센터 (admin-center)

어느 게임도 소유하지 않는 시리즈 전체 관리 허브. 각 게임의 기존 관리 Cloud Functions를 대체하지 않고 그대로 호출하며(새 승인/거절 로직을 중복 구현하지 않음), 여러 게임에 걸친 데이터만 한 화면에 모아서 보여준다.

권한 모델

  • 관리자(고정 이메일) — 항상 전체 권한
  • 인증 스트리머 — 관리자가 adminCenter/streamerPermissions에서 켠 권한만 사용 가능(스트리머 개인별이 아니라 전원 공통 스위치). 승인·거절·해제처럼 신원을 좌우하는 민감한 권한은 아직 위임 대상에 넣지 않았다

지금 구현된 기능

  • 인증 스트리머 관리 — 배팅시장·주식시장 양쪽의 대기 신청·인증 목록 통합 조회, 승인/거절/해제(각 게임 기존 함수 라우팅)
  • 감사 로그 통합 — 배팅시장 bettingMarket/auditLog + 주식시장 신설 adminAuditLog 병합 조회
  • 게임 콘텐츠 동결 상태 — 게임별 contentFreeze 토글(서비스 점검이 아니라 "신규 개발 중단, 버그 수정만" 라벨)
  • 인증 스트리머 권한 위임 — 위임 가능 권한 목록(카탈로그) 체리피크 UI
07

해야 할 작업

지금까지 논의·설계는 됐지만 아직 구현되지 않았거나, 의도적으로 미뤄둔 항목들. 우선순위 순으로 정리한다.

우선순위작업내용 / 이유
중간 즉시 회수 킬스위치 위임받은 인증 스트리머의 최근 조치를 한 번에 되돌리는 기능. 아직 실제로 위임된 권한이 없어 급하진 않지만, 권한 위임을 시작하기 전에 먼저 마련해야 안전하다 — 순서상 아래 "권한 카탈로그 채우기"보다 먼저 와야 함
중간 위임 권한 카탈로그 채우기 adminCenter/streamerPermissions 체리피크 메커니즘은 만들어졌지만 PERMISSION_CATALOG가 비어있어 실제로 위임 중인 권한이 하나도 없다. 승인·거절·해제처럼 신원을 좌우하는 민감한 권한은 제외하고, 낮은 리스크 항목(공지 등록, 배너 검수 등)부터 후보로 검토
낮음~중간 주식시장 감사 로그 확장 지금은 스트리머 인증 관련 액션 3개(승인·거절·해제)만 adminAuditLog에 기록 중. 주가 조정·배너·캐시충전 등 adminAction의 나머지 관리 액션(약 27개)까지 로깅 범위를 넓혀야 통합 관리 센터의 감사 로그 카드가 실제로 "전체" 로그가 된다
낮음 (보류 중) 콘텐츠 동결 플래그 실제 연동 seriesConfig/{gameId}/contentFreeze 토글은 관리 센터에서 켤 수 있지만, 어떤 게임 프론트엔드도 아직 이 값을 읽지 않아 실제 화면엔 영향이 없다. 각 게임에 "신규 콘텐츠 동결 중" 배너/제약을 연동하는 작업 필요 — 사용자가 명시적으로 후순위로 미룬 항목
낮음 (미정) 미드나잇 마트런 / 절대 광고를 클릭하지 마 온보딩 같은 GitHub Pages 오리진에 있지만 아직 공유 Firebase 프로젝트의 인증/재화 시스템과 연결되지 않은 독립 게임 2종. 편입하려면 03번의 apiKey 통일 + 통합 관리 센터의 GAME_CATALOG 등록이 필요
낮음 (사소함) grantAchievement("account_protected") 비대칭 수정 인증 경로에 따라 이 업적이 지급되거나 안 되거나 하는 사소한 불일치. 사용자 경험에 미치는 영향이 작아 지금까지 우선순위에서 밀려남 — 다른 작업 하는 김에 같이 처리하는 정도로 충분
권장 순서 — 킬스위치 → 권한 카탈로그 채우기 순으로 가는 게 안전하다. 위임 메커니즘이 이미 있다고 해서 카탈로그부터 채우면, 되돌릴 방법 없이 실제 권한이 스트리머 전원에게 뿌려지는 상태가 먼저 생긴다.
