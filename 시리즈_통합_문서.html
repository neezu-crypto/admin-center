Series Architecture Doc

스트리머 시리즈 통합 문서

여러 저장소·여러 게임이 하나의 Firebase 프로젝트를 공유하는 구조 — 코드만 봐서는 알기 어려운 부분을 기록한다
저장소 5개 공유 Firebase 프로젝트 soop-stock-market 1개 공유 오리진 neezu-crypto.github.io
01

이 문서가 존재하는 이유

이 시리즈는 게임마다 별도 저장소로 존재하지만, 인증·재화·관리 세션은 하나의 Firebase 프로젝트(soop-stock-market)를 여러 저장소가 함께 씀으로써 연결된다. 이 "공유"는 각 저장소의 코드만 따로 읽어서는 잘 드러나지 않고, 두 저장소를 동시에 봐야만 이해되는 경우가 많다.

이 문서의 목적 — 게임 기획(무엇을 만드는가)이 아니라, 저장소 사이의 연결 방식(어떻게 공유되는가)을 기록한다. 각 게임 고유 기획은 그 저장소의 자체 기획서 문서를 본다.

03

로그인 세션 자동 공유

배팅시장·주식시장·배경시장·통합 관리 센터에 각각 로그인해야 할 것 같지만, 실제로는 한 곳에서 로그인하면 나머지도 처음 방문 시 이미 로그인된 상태로 시작한다.

전제 조건 두 가지가 모두 맞아야 함: 1) 같은 오리진(scheme+host+port) → 전부 https://neezu-crypto.github.io (경로만 다름, CNAME 커스텀 도메인 없음) → 브라우저 저장소(IndexedDB)는 경로가 아니라 오리진 단위로만 분리됨 2) 같은 Firebase apiKey → Auth 세션은 firebase:authUser:{apiKey}:{앱이름} 키로 저장됨 → apiKey가 다르면 오리진이 같아도 완전히 별도 세션이 만들어짐
실제로 있었던 문제 — 주식시장의 프론트엔드(index.html)만 자기 고유 Web App의 다른 apiKey를 쓰고 있어서, 나머지 3곳과 오리진은 같은데도 세션이 안 섞였다. 주식시장의 apiKey를 나머지와 동일하게 맞추고 나서야 공유되기 시작했다. appId는 이 메커니즘과 무관(저장 키에 안 들어감) — interior-3d-viewer의 appId는 원래부터 배팅시장과 달랐지만 세션 공유엔 문제없었다.

즉 새 페이지/저장소를 이 시리즈에 편입시키려면, firebaseConfig의 apiKey를 반드시 기존 값과 동일하게 맞춰야 한다 — Firebase 콘솔에서 새 Web App을 등록해도 발급된 apiKey를 그대로 쓰면 안 되고, 기존 apiKey로 바꿔 써야 세션이 공유된다.

04

인증 스트리머 상태가 3곳에 걸쳐 있는 이유

uid(로그인 세션)는 위 방식으로 공유되지만, "이 uid가 인증 스트리머인가"를 판단하는 방식은 앱마다 다르다 — 그래서 uid 공유만으로는 인증 상태까지 자동으로 안 따라온다.

데이터주체내용
streamerVerifications공유 노드(두 앱이 같이 씀)SOOP 아이디를 canonical key로 삼는 인증 원장. 배팅시장은 이걸 uid로 직접 조회해서 판단
users/{uid}/streamerVerified주식시장 전용주식시장은 이 자체 캐시 플래그로 판단(공유 노드를 직접 안 봄) — "계정 보호" 등 자산 관련 특전의 기준
bettingMarket/profiles/{uid}배팅시장 전용인증 승인 시 채워지는 닉네임/SOOP아이디/아바타 — 안 채워지면 프로필이 초기 상태로 보임
실제로 있었던 문제 (3건 연쇄)
  • 매칭 키 비대칭 — 배팅시장은 SOOP 아이디로, 주식시장은 닉네임으로만 기존 레코드를 찾아서, 같은 사람이 두 앱에서 각각 인증받으면 uid가 다른 중복 레코드 두 개가 생겼다. → 양쪽 다 "SOOP 아이디 우선, 닉네임 폴백"으로 통일
  • 해제 비대칭 — 배팅시장의 인증 해제가 streamerVerifications만 지우고 users/{uid}/streamerVerified는 안 건드려서, 해제해도 주식시장에선 계속 "보호된 계정"으로 남았다. → 승인/해제 양쪽 함수가 서로의 플래그도 같이 정리하도록 수정
  • 프로필 비대칭 — 주식시장에서 인증해도 배팅시장 프로필은 안 채워져서, 배팅시장에 처음 들어가면 초기 상태로 보였다. → 주식시장의 승인 함수가 배팅시장 프로필도 같이 채우도록 수정
신규 uid 초기화 함정 — 주식시장의 users/{uid}는 "노드가 존재하면 이미 초기화된 계정"으로 취급해 시작 자금(1,000,000원)을 안 준다. 그래서 배팅시장 쪽에서 이 uid의 플래그를 미리 써넣을 때는 노드가 아직 없으면 시작 자금까지 같이 채워서 만들어야 한다(그냥 플래그 하나만 쓰면 나중에 실제 접속했을 때 돈을 못 받는 사고가 남).

06

통합 관리 센터 (admin-center)

어느 게임도 소유하지 않는 시리즈 전체 관리 허브. 각 게임의 기존 관리 Cloud Functions를 대체하지 않고 그대로 호출하며(새 승인/거절 로직을 중복 구현하지 않음), 여러 게임에 걸친 데이터만 한 화면에 모아서 보여준다.

권한 모델

  • 관리자(고정 이메일) — 항상 전체 권한
  • 인증 스트리머 — 관리자가 adminCenter/streamerPermissions에서 켠 권한만 사용 가능(스트리머 개인별이 아니라 전원 공통 스위치). 승인·거절·해제처럼 신원을 좌우하는 민감한 권한은 아직 위임 대상에 넣지 않았다

지금 구현된 기능

  • 인증 스트리머 관리 — 배팅시장·주식시장 양쪽의 대기 신청·인증 목록 통합 조회, 승인/거절/해제(각 게임 기존 함수 라우팅)
  • 감사 로그 통합 — 배팅시장 bettingMarket/auditLog + 주식시장 신설 adminAuditLog 병합 조회
  • 게임 콘텐츠 동결 상태 — 게임별 contentFreeze 토글(서비스 점검이 아니라 "신규 개발 중단, 버그 수정만" 라벨)
  • 인증 스트리머 권한 위임 — 위임 가능 권한 목록(카탈로그) 체리피크 UI
07

해야 할 작업

지금까지 논의·설계는 됐지만 아직 구현되지 않았거나, 의도적으로 미뤄둔 항목들. 우선순위 순으로 정리한다.

우선순위작업내용 / 이유
중간 즉시 회수 킬스위치 위임받은 인증 스트리머의 최근 조치를 한 번에 되돌리는 기능. 아직 실제로 위임된 권한이 없어 급하진 않지만, 권한 위임을 시작하기 전에 먼저 마련해야 안전하다 — 순서상 아래 "권한 카탈로그 채우기"보다 먼저 와야 함
중간 위임 권한 카탈로그 채우기 adminCenter/streamerPermissions 체리피크 메커니즘은 만들어졌지만 PERMISSION_CATALOG가 비어있어 실제로 위임 중인 권한이 하나도 없다. 승인·거절·해제처럼 신원을 좌우하는 민감한 권한은 제외하고, 낮은 리스크 항목(공지 등록, 배너 검수 등)부터 후보로 검토
낮음~중간 주식시장 감사 로그 확장 지금은 스트리머 인증 관련 액션 3개(승인·거절·해제)만 adminAuditLog에 기록 중. 주가 조정·배너·캐시충전 등 adminAction의 나머지 관리 액션(약 27개)까지 로깅 범위를 넓혀야 통합 관리 센터의 감사 로그 카드가 실제로 "전체" 로그가 된다
낮음 (보류 중) 콘텐츠 동결 플래그 실제 연동 seriesConfig/{gameId}/contentFreeze 토글은 관리 센터에서 켤 수 있지만, 어떤 게임 프론트엔드도 아직 이 값을 읽지 않아 실제 화면엔 영향이 없다. 각 게임에 "신규 콘텐츠 동결 중" 배너/제약을 연동하는 작업 필요 — 사용자가 명시적으로 후순위로 미룬 항목
낮음 (미정) 미드나잇 마트런 / 절대 광고를 클릭하지 마 온보딩 같은 GitHub Pages 오리진에 있지만 아직 공유 Firebase 프로젝트의 인증/재화 시스템과 연결되지 않은 독립 게임 2종. 편입하려면 03번의 apiKey 통일 + 통합 관리 센터의 GAME_CATALOG 등록이 필요
낮음 (사소함) grantAchievement("account_protected") 비대칭 수정 인증 경로에 따라 이 업적이 지급되거나 안 되거나 하는 사소한 불일치. 사용자 경험에 미치는 영향이 작아 지금까지 우선순위에서 밀려남 — 다른 작업 하는 김에 같이 처리하는 정도로 충분
중간 devbar 구성을 통합 관리 센터에서 관리 지금은 각 페이지에 하드코딩된 정적 링크 목록. 08번에서 상세 설계
높음 관리자 이메일 중복 하드코딩 정리 동일한 이메일 문자열이 4개 저장소·Functions/클라이언트/RTDB 규칙 3개 계층에 걸쳐 반복됨. 09번에서 상세 설계 — devbar보다 조용히 사고 날 확률이 높아 우선순위를 높게 잡음
중간 통합 관리 센터 — 페이지별 접속자 분석 시간당 최고 동시 접속자 수 + 페이지별/합산 스파크라인 차트. 10번에서 상세 설계
중간 통합 관리 센터 — 전체 통계 요약·이상 거래 모니터링 오늘/누적/재무 건전성/일간·주간·월간 통계 + 이상 거래 모니터링. 11번에서 상세 설계
권장 순서 — 킬스위치 → 권한 카탈로그 채우기 순으로 가는 게 안전하다. 위임 메커니즘이 이미 있다고 해서 카탈로그부터 채우면, 되돌릴 방법 없이 실제 권한이 스트리머 전원에게 뿌려지는 상태가 먼저 생긴다.
08

devbar를 통합 관리 센터에서 관리하기 (설계)

각 게임 페이지 상단의 devbar(사이트명 + "다른 게임 바로가기" 링크 목록)는 아직 코드에 그대로 박혀있는 정적 HTML이다.

현재 상태

저장소devbar 위치비고
StreamBet-Marketindex.html 1곳링크 목록이 그 파일에 직접 하드코딩
interior-3d-viewerindex.html · ski-resort.html · fireworks.html 3곳거의 동일한 목록이 3개 파일에 각각 복사돼 있음
soop-stock-marketindex.html — <nav class="topnav">이름과 마크업은 다르지만(devbar가 아니라 topnav, .topnav-btn) 같은 역할을 하는 목록이 독립적으로 하드코딩돼 있음 — 공유 컴포넌트가 아니라 각 저장소가 각자 베낀 사본이라 클래스명부터 이미 갈라진 상태
문제 — 새 게임이 추가되거나 링크 하나가 바뀔 때마다 사람이 여러 저장소의 여러 파일을 일일이(그것도 서로 다른 마크업/클래스명으로) 찾아 고쳐야 한다. 공유 코드가 아니라 각자 베낀 사본이다 보니 이미 이름부터 갈라졌고, 게임 수가 늘수록 어긋날 지점도 늘어난다.

제안하는 구조

1) devbar 링크 목록을 공유 RTDB 노드로 이동 → 예: seriesConfig/devbarLinks = [{ label, url, order }, ...] → .read: true (원래도 페이지에 노출되는 공개 링크), .write: Functions 전용 2) 각 페이지의 devbar 렌더링 스크립트가 로드 시점에 이 노드를 읽어서 링크를 그린다 → 06번 GAME_CATALOG와 마찬가지로 "한 곳만 고치면 전체에 반영"되는 패턴 3) 네트워크 실패 / 노드가 비어있는 경우를 대비해 지금의 하드코딩된 목록을 그대로 기본값(fallback)으로 남겨둔다 → devbar가 통째로 사라지는 사고를 방지

통합 관리 센터 쪽 작업

  • 새 카드 "devbar 구성" 추가 — 링크 추가/수정/삭제/순서 변경 UI
  • 저장 시 seriesConfig/devbarLinks를 갱신하는 Cloud Function(관리자 전용, 06번 setSeriesConfig류 패턴 재사용) + adminAuditLog 기록

영향 범위 (구현 시 손대야 할 파일)

  • StreamBet-Market/js/devbar.js — 지금은 마퀴 스크롤 계산만 함, 링크 목록을 RTDB에서 읽어와 DOM에 그리는 로직 추가 필요
  • interior-3d-viewer의 3개 페이지 — 각자 독립된 인라인 devbar 마크업이라 페이지마다 동일한 로직을 반복 적용해야 함
  • soop-stock-market/index.html — <nav class="topnav">/.topnav-btn 마크업이 devbar와 이름부터 다르므로, 공통 로직을 적용하려면 클래스명 통일 또는 별도 어댑터가 필요
권한 위임 후보로도 적합 — 링크 목록 수정은 신원·재화에 영향이 없는 낮은 리스크 작업이라, 07번 "위임 권한 카탈로그 채우기"의 첫 후보 항목으로 검토할 만하다.

관리자 이메일 중복 하드코딩

"누가 관리자인가"를 판단하는 기준이 하나의 공유 값이 아니라, 같은 이메일 문자열이 여러 저장소·여러 계층에 걸쳐 그대로 반복 입력된 것이다. devbar(08번)와 같은 계열의 "single source of truth 없음" 문제이지만, 영향 범위가 훨씬 넓고 조용히 사고 날 가능성도 더 크다.

개선 방향

지금: 이메일 문자열을 4개 저장소가 각자 소스에 박아넣고 비교 제안: "관리자 uid 목록"을 공유 노드 하나로 두고 전부 그걸 참조 → 예: adminCenter/adminUids/{uid} = true (이메일이 아니라 uid 기준 — 이메일 변경에도 안전) → Functions: 각자 상수 비교 대신 이 노드를 조회 → RTDB 규칙: auth.token.email === '...' 리터럴 대신 root.child('adminCenter/adminUids').child(auth.uid).exists() 로 교체 → 클라이언트 UI 판단: getAdminCenterState 같은 기존 호출 결과의 role 필드 재사용
규모가 있는 작업 — RTDB 규칙 리터럴을 걷어내는 것만 해도 파일당 10곳 넘게 고쳐야 하고, 3곳(StreamBet-Market/interior-3d-viewer 규칙 + 4개 Functions 코드베이스)을 동시에 정합성 있게 배포해야 해서 실수 여지가 크다. 07번 작업 표에 "높음" 우선순위로 등록했지만, 실제 착수 전에 변경 범위를 다시 한번 파일 단위로 전수 점검하는 게 안전하다.
10

통합 관리 센터 — 페이지별 접속자 분석 (설계)

목표: 통합 관리 센터에서 페이지(게임)별 시간당 최고 동시 접속자 수를 보여주고, 페이지 개별 / 전체 합산 접속자 수를 스파크라인 차트로 확인할 수 있게 한다.

현재 상태

저장소있는 것비고
soop-stock-market 실시간 "현재 접속자" 수 표시 presence/users/{uid}에 5분 주기로 lastSeen 하트비트를 쓰고, 클라이언트가 60분 유예를 두고 활성 uid 수를 세어 그 순간의 숫자만 보여준다. 이력을 저장하지 않아 "지금 몇 명"만 알 수 있고, 시간대별 추이나 최고치는 알 수 없다
StreamBet-Market 규칙만 존재, 기능 없음 database.rules.json에 presence/users/{uid} 노드 규칙이 정의돼 있지만, 이 노드를 실제로 읽거나 쓰는 코드가 저장소 어디에도 없다 — 예비로 만들어두고 아직 안 쓴 스키마로 보임
interior-3d-viewer · admin-center 없음 presence 관련 노드/코드 전무
설계상 반드시 짚어야 할 함정 — 03번에서 다뤘듯 uid는 로그인 세션 공유로 여러 페이지에서 동일하다. 그런데 soop-stock-market의 현재 스키마(presence/users/{uid})와 StreamBet-Market 규칙의 스키마 둘 다 앱 구분 없이 uid만으로 기록하는 구조다. 이 스키마를 그대로 다른 페이지에도 적용하면, 한 사람이 배팅시장 탭과 주식시장 탭을 동시에 열어놔도 같은 uid라서 presence 노드가 하나로 겹쳐 쓰기 경합이 나고, "어느 페이지에 접속 중인지" 자체를 구분할 수 없다. 페이지별 접속자 수를 세려면 반드시 앱 단위로 네임스페이스된 경로(presence/{appId}/{uid})로 먼저 정리해야 하고, 이 과정에서 soop-stock-market의 기존 경로도 함께 옮겨야 한다.

제안하는 파이프라인

1) 각 페이지가 하트비트 기록 (soop-stock-market의 기존 방식을 앱별로 네임스페이스만 바꿔 재사용) → presence/{appId}/{uid}: { lastSeen } (appId는 06번 GAME_CATALOG의 id와 동일하게) 2) 주기 실행되는 Cloud Scheduler 함수(onSchedule, 예: 5분마다)가 각 appId의 presence 노드를 훑어 유예시간 이내 활성 uid 수를 센다 3) 그 값이 현재 시간대(hour bucket)에 이미 기록된 최고치보다 크면 갱신 → analytics/presenceHourly/{appId}/{yyyyMMddHH}: { peak } 4) 오래된 버킷은 주기적으로 정리(예: 30일 이상 지난 데이터 삭제) → adminAuditLog의 200개 캡 정리와 같은 개념, 기준만 "개수"가 아니라 "기간"

통합 관리 센터 쪽 작업

  • 새 카드 "접속자 분석" — 게임별 스파크라인 + "오늘 시간당 최고 접속자 수" 라벨, 그리고 같은 시간 버킷끼리 합산한 전체 스파크라인
  • 새 조회 함수 getVisitorAnalytics(onCall, 관리자 전용) — 요청 범위(예: 최근 24시간/7일)의 시간별 peak을 앱별 + 합산으로 반환
  • 차트 렌더링은 soop-stock-market이 이미 쓰고 있는 Chart.js를 그대로 재사용 — 스파크라인은 축·범례 없는 미니 line chart로 충분

영향 범위

  • soop-stock-market — 기존 presence/users/{uid} 하트비트·현재 접속자 표시 로직을 presence/stockMarket/{uid}로 이전
  • StreamBet-Market · interior-3d-viewer(3개 페이지) — presence 하트비트를 새로 붙여야 함(지금은 없거나 죽은 규칙뿐)
  • 05번의 RTDB 규칙 동기화 관례에 따라, presence 스키마 변경과 analytics/presenceHourly 신설 모두 StreamBet-Market 원본에서 고치고 3곳에 동기화 후 배포
과금/부하 고려 — presence 하트비트는 활성 사용자당 주기적 쓰기라 사용자가 늘수록 RTDB 쓰기 횟수가 비례해서 늘어난다. 이미 soop-stock-market이 5분 주기로 검증한 값이라 그대로 재사용하되, 페이지 수가 늘어날수록(3→5개 이상) 총 쓰기량을 한 번 더 점검할 것.

통합 관리 센터 — 전체 통계 요약·이상 거래 모니터링 (설계)

  • "이상 거래 모니터링"이라는 이름에 비해 실제로 있는 건 원시 리스트뿐 — 지금 있는 getAnomalyMonitor는 "최근 가입/상위 잔액/환전량 상위" 나열이지 규칙 기반 탐지가 아니다. 통합 관리 센터에 이 이름을 그대로 쓰면 실제보다 더 많은 걸 하는 것처럼 보일 위험 — 1단계(기존 리스트 통합 표시)와 2단계(실제 스코어링/자동 플래깅 규칙 설계)를 분리해서 표기하는 게 정확하다
