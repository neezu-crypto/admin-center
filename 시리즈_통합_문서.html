스트리머 시리즈 통합 문서

여러 저장소·여러 게임이 하나의 Firebase 프로젝트를 공유하는 구조 — 코드만 봐서는 알기 어려운 부분을 기록한다
저장소 5개 공유 Firebase 프로젝트 soop-stock-market 1개 공유 오리진 neezu-crypto.github.io
01

이 문서가 존재하는 이유

이 시리즈는 게임마다 별도 저장소로 존재하지만, 인증·재화·관리 세션은 하나의 Firebase 프로젝트(soop-stock-market)를 여러 저장소가 함께 씀으로써 연결된다. 이 "공유"는 각 저장소의 코드만 따로 읽어서는 잘 드러나지 않고, 두 저장소를 동시에 봐야만 이해되는 경우가 많다.

이 문서의 목적 — 게임 기획(무엇을 만드는가)이 아니라, 저장소 사이의 연결 방식(어떻게 공유되는가)을 기록한다. 각 게임 고유 기획은 그 저장소의 자체 기획서 문서를 본다.

Functions 코드베이스가 여러 개인 이유 — 한 Firebase 프로젝트에 여러 저장소가 각자 firebase deploy를 실행하는 구조라, 이름이 우연히 겹치면 서로 덮어쓸 위험이 있다. presetgallery·admincenter처럼 격리된 코드베이스 이름을 쓰는 저장소는 로컬에서 "이 저장소가 뭘 배포/삭제 대상으로 볼지"를 좁히는 데는 도움이 된다. 배팅시장·주식시장은 아직 default 코드베이스를 그대로 쓰고 있어 이름 충돌 방지가 순전히 "안 겹치게 짓기"에 의존하는 상태다.
정정 — codebase가 달라도 함수 이름 충돌은 그대로 일어난다 — 09번 마이그레이션 도중 실제로 겪은 일: StreamBet-Market(default)과 interior-3d-viewer(presetgallery)가 각각 whoAmI라는 같은 이름의 함수를 배포했더니, codebase가 다른데도 나중에 배포한 쪽이 앞선 쪽을 그대로 덮어썼다. codebase는 firebase-tools가 로컬에서 "무엇을 내 책임으로 볼지" 구분하는 개념일 뿐, 실제 Cloud Functions 이름공간은 프로젝트+리전 단위로 전체가 공유된다. 즉 presetgallery·admincenter 같은 격리된 codebase도 이름 충돌 자체는 막아주지 않는다 — 결국 모든 저장소가 "안 겹치게 짓기"에 의존하는 건 마찬가지다. 새 함수를 추가할 땐 저장소를 가리지 않고 프로젝트 전체에서 그 이름이 이미 쓰이고 있는지 확인할 것(firebase functions:list --project soop-stock-market).
03

로그인 세션 자동 공유

배팅시장·주식시장·배경시장·통합 관리 센터에 각각 로그인해야 할 것 같지만, 실제로는 한 곳에서 로그인하면 나머지도 처음 방문 시 이미 로그인된 상태로 시작한다.

전제 조건 두 가지가 모두 맞아야 함: 1) 같은 오리진(scheme+host+port) → 전부 https://neezu-crypto.github.io (경로만 다름, CNAME 커스텀 도메인 없음) → 브라우저 저장소(IndexedDB)는 경로가 아니라 오리진 단위로만 분리됨 2) 같은 Firebase apiKey → Auth 세션은 firebase:authUser:{apiKey}:{앱이름} 키로 저장됨 → apiKey가 다르면 오리진이 같아도 완전히 별도 세션이 만들어짐
실제로 있었던 문제 — 주식시장의 프론트엔드(index.html)만 자기 고유 Web App의 다른 apiKey를 쓰고 있어서, 나머지 3곳과 오리진은 같은데도 세션이 안 섞였다. 주식시장의 apiKey를 나머지와 동일하게 맞추고 나서야 공유되기 시작했다. appId는 이 메커니즘과 무관(저장 키에 안 들어감) — interior-3d-viewer의 appId는 원래부터 배팅시장과 달랐지만 세션 공유엔 문제없었다.

즉 새 페이지/저장소를 이 시리즈에 편입시키려면, firebaseConfig의 apiKey를 반드시 기존 값과 동일하게 맞춰야 한다 — Firebase 콘솔에서 새 Web App을 등록해도 발급된 apiKey를 그대로 쓰면 안 되고, 기존 apiKey로 바꿔 써야 세션이 공유된다.

04

인증 스트리머 상태가 3곳에 걸쳐 있는 이유

uid(로그인 세션)는 위 방식으로 공유되지만, "이 uid가 인증 스트리머인가"를 판단하는 방식은 앱마다 다르다 — 그래서 uid 공유만으로는 인증 상태까지 자동으로 안 따라온다.

데이터주체내용
streamerVerifications공유 노드(두 앱이 같이 씀)SOOP 아이디를 canonical key로 삼는 인증 원장. 배팅시장은 이걸 uid로 직접 조회해서 판단
users/{uid}/streamerVerified주식시장 전용주식시장은 이 자체 캐시 플래그로 판단(공유 노드를 직접 안 봄) — "계정 보호" 등 자산 관련 특전의 기준
bettingMarket/profiles/{uid}배팅시장 전용인증 승인 시 채워지는 닉네임/SOOP아이디/아바타 — 안 채워지면 프로필이 초기 상태로 보임
실제로 있었던 문제 (3건 연쇄)
  • 매칭 키 비대칭 — 배팅시장은 SOOP 아이디로, 주식시장은 닉네임으로만 기존 레코드를 찾아서, 같은 사람이 두 앱에서 각각 인증받으면 uid가 다른 중복 레코드 두 개가 생겼다. → 양쪽 다 "SOOP 아이디 우선, 닉네임 폴백"으로 통일
  • 해제 비대칭 — 배팅시장의 인증 해제가 streamerVerifications만 지우고 users/{uid}/streamerVerified는 안 건드려서, 해제해도 주식시장에선 계속 "보호된 계정"으로 남았다. → 승인/해제 양쪽 함수가 서로의 플래그도 같이 정리하도록 수정
  • 프로필 비대칭 — 주식시장에서 인증해도 배팅시장 프로필은 안 채워져서, 배팅시장에 처음 들어가면 초기 상태로 보였다. → 주식시장의 승인 함수가 배팅시장 프로필도 같이 채우도록 수정
신규 uid 초기화 함정 — 주식시장의 users/{uid}는 "노드가 존재하면 이미 초기화된 계정"으로 취급해 시작 자금(1,000,000원)을 안 준다. 그래서 배팅시장 쪽에서 이 uid의 플래그를 미리 써넣을 때는 노드가 아직 없으면 시작 자금까지 같이 채워서 만들어야 한다(그냥 플래그 하나만 쓰면 나중에 실제 접속했을 때 돈을 못 받는 사고가 남).

06

통합 관리 센터 (admin-center)

어느 게임도 소유하지 않는 시리즈 전체 관리 허브. 각 게임의 기존 관리 Cloud Functions를 대체하지 않고 그대로 호출하며(새 승인/거절 로직을 중복 구현하지 않음), 여러 게임에 걸친 데이터만 한 화면에 모아서 보여준다.

권한 모델

  • 관리자(고정 이메일) — 항상 전체 권한
  • 인증 스트리머 — 관리자가 adminCenter/streamerPermissions에서 켠 권한만 사용 가능(스트리머 개인별이 아니라 전원 공통 스위치). 승인·거절·해제처럼 신원을 좌우하는 민감한 권한은 아직 위임 대상에 넣지 않았다

지금 구현된 기능

  • 인증 스트리머 관리 — 배팅시장·주식시장 양쪽의 대기 신청·인증 목록 통합 조회, 승인/거절/해제(각 게임 기존 함수 라우팅)
  • 감사 로그 통합 — 배팅시장 bettingMarket/auditLog + 주식시장 신설 adminAuditLog 병합 조회
  • 게임 콘텐츠 동결 상태 — 게임별 contentFreeze 토글(서비스 점검이 아니라 "신규 개발 중단, 버그 수정만" 라벨)
  • 인증 스트리머 권한 위임 — 위임 가능 권한 목록(카탈로그) 체리피크 UI

관리자 이메일 중복 하드코딩 완료

"누가 관리자인가"를 판단하는 기준이 하나의 공유 값이 아니라, 같은 이메일 문자열이 여러 저장소·여러 계층에 걸쳐 그대로 반복 입력된 것이었다. devbar(08번)와 같은 계열의 "single source of truth 없음" 문제이지만, 영향 범위가 훨씬 넓고 조용히 사고 날 가능성도 더 컸다. 아래 "문제" 부분은 마이그레이션 착수 전 상태의 기록이고, 실제로는 전부 완료돼 지금은 해당하지 않는다 — "실제로 완료한 내용"을 먼저 본다.

실제로 완료한 내용

1) 공유 노드 신설 — adminCenter/adminUids/{uid} = true (05번 관례대로 .read:false, .write:false) 2) 1회성 부트스트랩 — bootstrapAdminUid(admin-center)가 기존 이메일 비교로 신원을 마지막 한 번 확인한 뒤, 호출자의 uid를 이 노드에 등록 3) Functions 4곳 전부 — isAdminUid/isAdmin 헬퍼 추가(uid 우선, 아직 uid가 등록 안 된 계정만 이메일로 폴백 + 폴백 사용 시 로그 경고). admin-center · StreamBet-Market(lib/auth.js) · soop-stock-market(common.js) · interior-3d-viewer(index.js) 각각의 requireAdmin류 함수와, 파일 곳곳에 흩어져 직접 이메일을 비교하던 지점(StreamBet-Market 3개 파일, soop-stock-market 2개 파일)까지 전부 이 헬퍼로 교체 4) 클라이언트 UI 판별 — adminCenter/adminUids는 .read:false라 브라우저가 직접 못 읽으므로, 앱마다 가벼운 전용 조회 함수를 새로 두고 그 결과를 캐싱해서 관리자 전용 버튼/화면 표시 여부를 결정하도록 전환 (StreamBet-Market: whoAmI / soop-stock-market: stockWhoAmI / interior-3d-viewer: galleryWhoAmI — 왜 이름이 다른지는 아래 참고) 5) RTDB 규칙 — StreamBet-Market·interior-3d-viewer 규칙 파일의 auth.token.email === '...' 리터럴 11곳을 전부 root.child('adminCenter/adminUids').child(auth.uid).exists() 로 교체
구현 중 실제로 겪은 사고 — codebase 격리는 함수 이름 충돌을 막아주지 않는다 — 4단계에서 각 앱의 신규 함수 이름을 처음엔 전부 whoAmI로 지었다. StreamBet-Market(default codebase)과 interior-3d-viewer(presetgallery codebase)에 각각 배포했는데, codebase가 달라도 실제 Cloud Functions 이름공간은 프로젝트 전체에서 하나로 공유돼서, 나중에 배포한 쪽이 먼저 배포한 쪽을 그대로 덮어썼다(02번에서 이론적으로만 우려했던 지점이 실제로 발생). 마침 두 구현의 로직이 사실상 동일해서 기능적으로는 우연히 문제가 안 됐지만, 발견 즉시 whoAmI(StreamBet-Market) / stockWhoAmI(soop-stock-market) / galleryWhoAmI(interior-3d-viewer)로 이름을 구분해서 재배포했다. 같은 프로젝트를 공유하는 저장소들이 새 함수를 추가할 땐, codebase가 다르다는 이유로 이름이 겹쳐도 괜찮다고 가정하면 안 된다 — 이후 새 함수를 만들 때마다 이 사고를 기준으로 이름을 점검할 것.

제안했던 방향(uid 기준 공유 노드 + 단계적 전환) 그대로 실행됐다. RTDB 규칙 리터럴 11곳, Functions 4개 저장소, 클라이언트 3곳까지 전부 정합성 있게 배포됐고, 마이그레이션 도중에는 서버 코드에는 이메일 폴백을 남겨 배포 순서가 어긋나도 관리자가 스스로 잠기지 않도록 안전장치를 뒀다(RTDB 규칙은 uid가 이미 등록된 걸 확인한 뒤 폴백 없이 바로 전환). 실제로 작업 도중 예상 못 한 문제(위 콜아웃의 Cloud Functions 이름 충돌)도 하나 발견해 해결했다 — 계획대로만 되지 않는다는 걸 보여주는 사례로 남겨둔다.

통합 관리 센터 — 페이지별 접속자 분석 (설계)

목표: 통합 관리 센터에서 페이지(게임)별 시간당 최고 동시 접속자 수를 보여주고, 페이지 개별 / 전체 합산 접속자 수를 스파크라인 차트로 확인할 수 있게 한다.

현재 상태

저장소있는 것비고
soop-stock-market 실시간 "현재 접속자" 수 표시 presence/users/{uid}에 5분 주기로 lastSeen 하트비트를 쓰고, 클라이언트가 60분 유예를 두고 활성 uid 수를 세어 그 순간의 숫자만 보여준다. 이력을 저장하지 않아 "지금 몇 명"만 알 수 있고, 시간대별 추이나 최고치는 알 수 없다
StreamBet-Market 규칙만 존재, 기능 없음 database.rules.json에 presence/users/{uid} 노드 규칙이 정의돼 있지만, 이 노드를 실제로 읽거나 쓰는 코드가 저장소 어디에도 없다 — 예비로 만들어두고 아직 안 쓴 스키마로 보임
interior-3d-viewer · admin-center 없음 presence 관련 노드/코드 전무
설계상 반드시 짚어야 할 함정 — 03번에서 다뤘듯 uid는 로그인 세션 공유로 여러 페이지에서 동일하다. 그런데 soop-stock-market의 현재 스키마(presence/users/{uid})와 StreamBet-Market 규칙의 스키마 둘 다 앱 구분 없이 uid만으로 기록하는 구조다. 이 스키마를 그대로 다른 페이지에도 적용하면, 한 사람이 배팅시장 탭과 주식시장 탭을 동시에 열어놔도 같은 uid라서 presence 노드가 하나로 겹쳐 쓰기 경합이 나고, "어느 페이지에 접속 중인지" 자체를 구분할 수 없다. 페이지별 접속자 수를 세려면 반드시 앱 단위로 네임스페이스된 경로(presence/{appId}/{uid})로 먼저 정리해야 하고, 이 과정에서 soop-stock-market의 기존 경로도 함께 옮겨야 한다.

제안하는 파이프라인

1) 각 페이지가 하트비트 기록 (soop-stock-market의 기존 방식을 앱별로 네임스페이스만 바꿔 재사용) → presence/{appId}/{uid}: { lastSeen } (appId는 06번 GAME_CATALOG의 id와 동일하게) 2) 주기 실행되는 Cloud Scheduler 함수(onSchedule, 예: 5분마다)가 각 appId의 presence 노드를 훑어 유예시간 이내 활성 uid 수를 센다 3) 그 값이 현재 시간대(hour bucket)에 이미 기록된 최고치보다 크면 갱신 → analytics/presenceHourly/{appId}/{yyyyMMddHH}: { peak } 4) 오래된 버킷은 주기적으로 정리(예: 30일 이상 지난 데이터 삭제) → adminAuditLog의 200개 캡 정리와 같은 개념, 기준만 "개수"가 아니라 "기간"

통합 관리 센터 쪽 작업

  • 새 카드 "접속자 분석" — 게임별 스파크라인 + "오늘 시간당 최고 접속자 수" 라벨, 그리고 같은 시간 버킷끼리 합산한 전체 스파크라인
  • 새 조회 함수 getVisitorAnalytics(onCall, 관리자 전용) — 요청 범위(예: 최근 24시간/7일)의 시간별 peak을 앱별 + 합산으로 반환
  • 차트 렌더링은 soop-stock-market이 이미 쓰고 있는 Chart.js를 그대로 재사용 — 스파크라인은 축·범례 없는 미니 line chart로 충분

영향 범위

  • StreamBet-Market · interior-3d-viewer(3개 페이지) — presence 하트비트를 새로 붙여야 함(지금은 없거나 죽은 규칙뿐)
  • 05번의 RTDB 규칙 동기화 관례에 따라, presence 스키마 변경과 analytics/presenceHourly 신설 모두 StreamBet-Market 원본에서 고치고 3곳에 동기화 후 배포

1) 검색어(닉네임/uid/SOOP 아이디) 입력 → StreamBet-Market의 bettingMarket/profiles, 공유 streamerVerifications(05번)를 prefix 검색(orderByChild().startAt()~endAt())으로 조회해 후보 uid 목록을 얻는다 → StreamBet-Market의 기존 검색은 "정확히 일치"만 지원하므로, prefix 검색은 통합 관리 센터에서 새로 추가하는 부분(부분 검색은 어디에도 없던 신규 기능) 2) 후보 중 하나(또는 이미 아는 uid)를 선택하면 getUserOverview({ uid })(onCall, 관리자 전용) 호출 → StreamBet-Market adminLookupUser 로직 + soop-stock-market actionGetUserDetail을 내부적으로 병렬 호출해 하나의 응답으로 합친다 (06번 패턴 재사용) → 12번의 getPurchaseOverview({ uid })도 같은 화면에 이어붙임 3) 화면 구성: 상단에 식별 정보(닉네임·uid·인증 상태), 그 아래 게임별 섹션(배팅시장 잔액/베팅내역, 주식시장 현금/보유종목), 맨 아래 구매 이력(12번)
정지·잔액조정 같은 액션은 그대로 각 게임 함수로 — StreamBet-Market의 banAccount/adminAdjustBalance 등 실제 조치는 새로 만들지 않고 기존 함수를 그대로 호출한다(06번 원칙). soop-stock-market 쪽엔 정지 자체가 없다는 게 20번에서 확인됨 — 그쪽 uid 정지는 20번의 설계가 먼저 필요하다.

통합 관리 센터 — 관리자·인증 스트리머 전용 채팅 (설계)

목표: 관리자와 인증 스트리머끼리 실시간으로 소통하는 채팅을 통합 관리 센터에서도 쓸 수 있게 한다. 이 문서의 다른 항목과 달리 이미 완성된 기능을 넓히는 작업이라는 점이 다르다.

현재 상태

StreamBet-Market에 이미 완전한 형태로 구현돼 있다.

  • sendAdminChatMessage({ text })(functions/src/chat.js) — requireAdminOrVerifiedStreamer 가드, 300자 제한(CHAT_MESSAGE_MAX_LENGTH), bettingMarket/profiles에서 닉네임·아바타를 자동으로 붙여서 bettingMarket/adminChat에 기록
  • capped-log.js의 trimToLast로 최근 200개만 유지, 클라이언트(js/admin-chat.js)도 limitToLast(200)으로만 구독 — 05번·10번에서 반복된 "무한정 쌓이는 로그성 노드는 캡을 둔다" 원칙과 동일
  • 관리 탭 상단에서 이미 실시간으로 동작 중
가드가 이미 안전하게 짜여 있다 — requireAdminOrVerifiedStreamer는 bettingMarket/verifiedStreamerUids 미러가 아니라 공유 streamerVerifications 노드를 uid로 직접 조회한다(admin-center 자체 가드와 동일한 방식). 04번에서 다룬 미러 동기화 문제와 무관하게, 어느 게임에서 인증받았든 이 채팅에는 즉시 접근 가능하다는 뜻 — 이 부분은 추가로 손볼 게 없다.

soop-stock-market·interior-3d-viewer·admin-center엔 이런 기능이 없다.

문제

이 채팅이 StreamBet-Market의 관리 탭 안에만 있어서, 그 페이지를 평소에 열지 않는 인증 스트리머나 관리자는 대화 자체를 놓친다. "관리자·인증 스트리머 전용 소통 채널"이라는 취지를 살리려면 시리즈 어디서든(특히 여러 게임을 오가는 관리자가 상시 열어두는 통합 관리 센터에서) 접근 가능해야 한다.

제안하는 구조 — 두 가지 선택지

선택지방식장단점
A. 기존 채널 재사용 (추천) admin-center UI가 StreamBet-Market이 이미 배포한 sendAdminChatMessage를 그대로 httpsCallable로 호출하고, bettingMarket/adminChat을 그대로 구독 새 Function 불필요, 기존 대화 이력 유지, 06번 원칙과 정확히 일치. 같은 Firebase 프로젝트 안에서는 codebase가 달라도 함수 이름만 맞으면 다른 저장소에서 배포한 함수를 그대로 호출할 수 있다(codebase는 배포 단위 구분일 뿐 호출 범위를 제한하지 않음)
B. admin-center 전용 새 채널 adminCenter/chat 신설, 같은 로직을 admin-center 쪽에 복제 소유권은 깔끔하지만 대화가 두 갈래로 갈라지고(어디를 봐야 최신 대화인지 헷갈림), 이미 검증된 로직을 그대로 베끼는 것이라 실익이 없음

A를 따르면 admin-center 쪽에서 할 일은 새 카드 "관리자·인증 스트리머 채팅" UI 하나뿐이다.

통합 관리 센터 — 검수 알람 (설계)

목표: 13번(페이지별 검수)·14번(구매 승인)·15번(종목 상장) 큐에 새 항목이 들어왔을 때 관리자·인증 스트리머가 놓치지 않게 한다.

현재 상태 — StreamBet-Market에 재사용할 만한 패턴이 이미 있다

js/admin-alerts.js의 "관리 탭 검수 알림 배너": 이미 각자 실시간 구독으로 그려지는 6개 목록(admin-pending-list·report-queue-list·nick-report-queue-list·verify-requests-list·chest-purchase-requests-list·streamer-requests-list)의 DOM을 MutationObserver로 지켜보다가, 항목 수가 바뀔 때마다 배지 숫자를 다시 계산한다. 각 목록의 데이터 구독 로직은 전혀 건드리지 않고 이미 그려진 결과만 관찰하므로 다른 모듈과 결합되지 않는다는 게 장점 — 클릭하면 해당 섹션으로 스크롤 이동.

이건 "알람"이라기보다 "배지"다 — 소리도, 브라우저 알림도, 다른 기기로 가는 알림도 없다. 그 관리 탭을 열어서 보고 있어야만 보이는 숫자 하나일 뿐이다. 시리즈 전체를 통틀어 이보다 더 적극적인 알림 수단(푸시 알림·사운드·외부 채널)은 어디에도 없다.

admin-center에 그대로 옮길 때 부딪히는 선행 조건

admin-center의 기존 데이터 갱신 방식과 맞지 않는다 — 06번에서 세운 admin-center의 조회 함수들(listStreamerVerificationOverview·listAuditLogOverview 등)은 전부 단발성 호출이다(코드 주석에 명시된 의도적 트레이드오프 — 실시간 onValue 구독을 쓰지 않음). 그런데 admin-alerts.js의 배지는 "이미 실시간으로 갱신되는 DOM"을 관찰하는 전제로 동작한다. admin-center의 13·14·15번 카드가 지금처럼 수동 새로고침 방식으로 남아있으면, 배지도 새로고침해야만 갱신되는 숫자가 되어 "알람"으로서 의미가 크게 줄어든다. 배지를 실시간으로 만들려면 해당 카드들을 먼저 onValue 구독 방식으로 바꿔야 하는데, 이건 admin-center가 처음에 의도적으로 피했던 선택이라 — 되돌릴지 여부부터 결정이 필요하다

제안하는 3단계

단계내용선행 조건
1단계 — 배지 재사용 admin-alerts.js와 같은 패턴을 admin-center의 13·14·15 카드에 그대로 적용. 카드가 열려있고 보고 있을 때만 숫자가 정확 없음 — 지금 방식(단발성 새로고침) 그대로도 "새로고침을 누르면 최신 숫자가 보이는" 수준까진 바로 가능
2단계 — 실시간 배지 탭을 열어두면 새로 고침 없이도 숫자가 즉시 바뀜 13·14·15 카드를 onValue 구독으로 전환 — admin-center의 기존 설계 방침을 부분적으로 뒤집는 결정
3단계 — 진짜 알림 탭을 안 보고 있어도 알 수 있음(브라우저 푸시 알림·사운드·카카오톡/디스코드 웹훅 등) 시리즈 전체에 전례가 전혀 없는 신규 기능 — 필요성부터 별도로 판단할 것(예: 상장 신청처럼 급하지 않은 것과, 인증 신청처럼 빨리 봐야 하는 것을 같은 수준으로 알릴 필요는 없을 수 있음)
권장 — 1단계는 지금 바로 붙일 수 있다. 2단계로 갈지는 admin-center를 관리자가 얼마나 상시로 켜두는지에 달려있고, 3단계는 실제로 검수가 늦어져서 문제가 된 사례가 쌓인 뒤에 판단해도 늦지 않다.
3단계 구체화 — 디스코드 웹훅으로 3단계를 실제로 설계한 내용은 24번에서 다룬다.

통합 관리 센터 — 세션 빠른 이동 (설계)

목표: 카드가 계속 늘어나는 통합 관리 센터에, 페이지 우측에 고정된 채로 클릭하면 해당 섹션으로 바로 스크롤 이동하는 목차 패널을 둔다.

현재 상태 — soop-stock-market에 이미 있는 패턴

soop-stock-market 관리자 페이지의 #admin-quicknav: 화면 우측에 고정된 내비게이션으로, QUICKNAV_ITEMS 배열(섹션 id·라벨 27개를 하드코딩)을 renderQuickNav()가 버튼 목록으로 그리고, 클릭하면 scrollIntoView({ behavior: 'smooth', block: 'start' })로 이동한다. 좁은 화면에서는 @media 쿼리로 아예 숨김 처리. 관리자 로그인 성공 시 한 번 렌더링되는 정적인 목차다.

StreamBet-Market·interior-3d-viewer·admin-center엔 이런 전체 목차가 없다. StreamBet-Market의 admin-alerts.js(18번)도 클릭 시 스크롤 이동은 하지만, 그건 대기 항목이 있는 6개 검수 섹션에 한정된 배지이지 전체 섹션을 나열하는 목차가 아니다.

왜 지금 이게 admin-center에 필요해지는가 — soop-stock-market이 이 패널을 만든 이유는 관리자 페이지 섹션이 27개까지 늘어났기 때문이다. 그런데 이 문서 08~18번에서 이미 설계한 카드만 세어봐도 devbar 구성·접속자 분석·전체 통계·구매 현황·페이지별 검수·구매 승인 검수·종목 상장 관리·유저 검색·채팅·검수 알람까지 10개가 기존 4개 카드(인증 스트리머 관리·감사 로그·콘텐츠 동결·권한 위임)에 더해진다. 다 구현하면 admin-center도 soop-stock-market과 똑같이 "카드가 너무 많아서 스크롤이 길어지는" 상태에 도달한다 — 같은 문제를 이미 풀어놓은 패턴이 바로 옆 저장소에 있는 셈이다.

제안하는 구조

  • soop-stock-market의 QUICKNAV_ITEMS 패턴을 그대로 이식 — admin-center 자체 카드 id 기준으로 새 배열을 작성(예: 인증 스트리머 관리·감사 로그·콘텐츠 동결·권한 위임·devbar 구성·접속자 분석·전체 통계·구매 현황·페이지별 검수·구매 승인 검수·종목 상장 관리·유저 검색·채팅·검수 알람)
  • 모바일에서 숨기는 처리도 동일하게 적용 — 좁은 화면에서 고정 패널이 콘텐츠를 가리지 않게
수동 관리 포인트 — 08번의 GAME_CATALOG처럼, 이 목차 배열도 카드가 추가/제거될 때마다 사람이 같이 고쳐야 자동으로 늘어나지 않는다. 새 카드를 붙이면서 이 배열에 항목 추가하는 걸 빠뜨리면, 그 카드만 목차에서 빠진 채로 조용히 방치될 수 있다.

정지가 새는 지점 — 03번에서 다뤘듯 로그인 세션(uid)은 앱 간에 공유된다. 그런데 정지는 StreamBet-Market 혼자만의 판단(bettingMarket/bannedAccounts)이고 soop-stock-market엔 이걸 검사하는 코드 자체가 없으므로, 배팅시장에서 정지된 유저가 같은 계정으로 로그인한 채 주식시장에서는 아무 제약 없이 계속 활동할 수 있다. 04번에서 다룬 "인증 상태가 한쪽에만 반영되는" 문제와 같은 패턴이지만, 이번엔 허용해야 할 걸 놓치는 게 아니라 막아야 할 걸 놓치는 방향이라 더 심각하다.

제안하는 구조

1단계 (바로 가능) — 통합 관리 센터에 "정지계정 관리" 카드 신설 → StreamBet-Market의 bettingMarket/bannedAccounts를 그대로 조회하고 banAccount/unbanAccount를 그대로 라우팅 (06번 원칙, 새 로직 없음) → 16번의 유저 상세 조회 화면에도 정지/해제 버튼을 바로 노출 2단계 (더 큰 작업) — soop-stock-market에도 실제 차단 효력을 만든다 → 04번에서 배운 교훈 재사용: 처음부터 앱별로 각자 정지 노드를 두지 말고 uid 기준 공유 원장 하나로 설계 (05번의 admin-only 규칙 패턴) → soop-stock-market의 거래·구매 관련 함수 진입부에도 StreamBet-Market의 assertNotBanned와 동등한 가드를 새로 추가해야 함 (기존에 없던 코드라 이건 정말 새로 만드는 부분)
왜 공유 원장 하나로 시작해야 하는가 — 04번에서 인증 상태를 앱마다 따로 캐싱해서 세 번이나 동기화 사고가 났던 걸 이미 겪었다. 정지 기능을 지금 StreamBet-Market 것을 미러링하는 방식으로 soop-stock-market에 새로 붙이면 같은 실수를 반복하게 된다. 처음부터 정지 여부를 판단하는 원장을 하나로 두고 두 게임이 같은 곳을 보게 만드는 게, 이 시리즈가 이미 두 번 배운 교훈을 실제로 적용하는 지점이다.

통합 관리 센터 — 게시글 홍보 현황 (설계, 게임 전체로 확장)

목표: StreamBet-Market에만 있는 "게시글 홍보 현황"(promotedStreamers) 개념을, 다른 기존 게임(soop-stock-market·interior-3d-viewer)과 앞으로 출시될 게임까지 게임을 가리지 않고 쓸 수 있는 통합 관리 센터 기능으로 만든다. 08번(devbar)·11번(통계)처럼 "게임별로 각자 만들지 말고 admin-center가 공통 틀을 소유"하는 패턴이다.

먼저 정확히 알아야 할 것 — 지금 있는 건 뭔가

bettingMarket/promotedStreamers는 결제·승인이 전혀 없는 관리자 개인 체크리스트다. 관리자가 어떤 스트리머의 SOOP 방송국 게시판에 직접 홍보글을 올린 뒤, "이미 홍보했음"을 기록해 중복 게시를 막는 용도 — 인증 여부와 무관하게 아무 닉네임이나 등록 가능하다. addPromotedStreamer/removePromotedStreamer(관리자 전용)로 이미 구현돼 있고, js/promoted-streamers.js가 자동완성 입력 + 실시간 칩 목록 UI까지 완비돼 있다. soop-stock-market의 배너·핀은 "글"이 아니라 종목을 노출시키는 유료 기능이라 이것과는 방향이 반대(관리자가 밖에 홍보 vs 유저가 결제해서 노출을 삼)이고 이미 14번에서 다뤘으므로, 이 22번은 promotedStreamers 쪽 개념만 확장한다.

일반화가 쉬운 이유 — 이 기능엔 게임별로 다른 로직이 원래 하나도 없었다(결제 없음, 승인 없음, 대상 검증도 없음 — 그냥 자유 텍스트 닉네임 + 시각). 그래서 "게임마다 다른 처리"를 새로 설계할 필요 없이, 어떤 게임이든 자유 텍스트 라벨 하나 + 시각만 있으면 그대로 재사용된다. 12번(구매 현황)이나 13번(검수)처럼 게임마다 데이터 형태가 달라 정규화가 필요했던 것과 다르게, 이건 원래부터 게임 중립적인 데이터였다.

제안하는 구조

1) 새 공유 노드로 이전 — adminCenter/promotedContent/{gameId}/{entryId} → { label, addedAt, addedBy } (label = 기존의 nickname과 같은 자유 텍스트) → .read: false, .write: false (Functions 전용, 05번 관례와 동일) → gameId는 06번 GAME_CATALOG의 id 재사용 — 새 게임은 그 배열에 한 줄만 추가하면 이 기능도 자동으로 그 게임을 지원 2) admin-center에 새 함수 3개(관리자 전용) listPromotedContent() — GAME_CATALOG 순서로 게임별 목록을 묶어서 반환 addPromotedContent({ gameId, label }) removePromotedContent({ gameId, entryId }) 3) 새 카드 "게시글 홍보 현황" — 08번 콘텐츠 동결 카드처럼 게임별로 구분된 섹션, 각 섹션에 자유 텍스트 입력 + 칩 목록(기존 UI 패턴 재사용)
기존 데이터 이전이 필요하다 — bettingMarket/promotedStreamers엔 이미 실제로 쌓인 이력이 있다. 새 노드로 옮길 때 한 번 데이터를 복사해야 하고({gameId: 'bettingMarket'}로 마이그레이션), 이후 StreamBet-Market의 기존 js/promoted-streamers.js는 그대로 옛 노드를 보게 둘지, 새 함수를 호출하도록 같이 고칠지 정해야 한다. 그대로 두면 같은 정보를 두 곳에서 따로 관리하게 돼 admin-center 쪽 목록과 어긋날 수 있다 — 04번에서 반복해서 겪은 "미러가 두 개 생기는" 패턴을 피하려면, StreamBet-Market 쪽도 결국 새 함수를 호출하도록 옮기는 게 맞다

이 구조라면 soop-stock-market·interior-3d-viewer, 그리고 앞으로 나올 게임도 별도 개발 없이 admin-center 화면에 새 섹션만 하나 더 생기는 방식으로 이 기능을 바로 쓸 수 있다.

통합 관리 센터 — 디스코드 웹훅 검수 알림 (설계)

목표: 18번의 3단계("탭을 안 보고 있어도 알림")를 디스코드 웹훅으로 구체화한다. 관리자가 admin-center를 켜두지 않아도, 검수 대기 항목이 생기는 순간 지정된 디스코드 채널에 메시지가 온다.

디스코드 웹훅이 하는 일

디스코드 채널마다 발급할 수 있는 URL 하나에 정해진 형식의 JSON을 POST하면, 그 채널에 메시지가 즉시 게시된다. 로그인이나 별도 인증이 필요 없다 — 즉 이 URL 자체가 비밀번호와 같은 민감정보다. 유출되면 누구나 그 채널에 메시지를 보낼 수 있게 된다.

핵심 설계 통찰 — admin-center가 다른 저장소를 건드리지 않고도 걸 수 있다

17번에서 확인했듯 codebase는 배포 단위 구분일 뿐, 같은 Firebase 프로젝트 안에서는 어느 codebase가 배포했든 실행 범위에 제약이 없다. RTDB 트리거(onValueCreated 등)도 마찬가지다 — 트리거는 "이 경로에 새 데이터가 생기면"을 감시할 뿐, 그 경로에 누가(어느 codebase가) 썼는지는 안 가린다. 그래서 admin-center의 functions/index.js에 새 트리거 함수들을 추가하는 것만으로, StreamBet-Market·soop-stock-market의 기존 신청 함수는 한 줄도 고치지 않고 그 함수들이 쓰는 RTDB 경로를 감시할 수 있다 — 06번 원칙("기존 로직 재사용, 새로 안 만든다")의 또 다른 적용이다.

메시지 설계

  • 어떤 큐인지(예: "🔔 새 마켓 신고"), 핵심 정보 1~2줄(신청자/사유 등 최소한만 — 민감정보 과다 노출 방지), admin-center로 바로 가는 링크를 포함한다
  • 딥링크는 19번(세션 빠른 이동)의 앵커 id를 URL 프래그먼트로 재사용하면 별도 라우팅 없이 바로 만들어진다(예: https://neezu-crypto.github.io/admin-center/?section=review#section-report) — 19번을 먼저 설계해둔 게 여기서 그대로 이어진다

보안·운영

  • 웹훅 URL은 Firebase Functions v2의 defineSecret으로 관리 — 코드·저장소 어디에도 평문으로 커밋하지 않는다(09번에서 다룬 "민감정보를 코드에 박아두지 않는다"는 원칙과 같은 결)
  • RTDB 규칙과는 무관 — 알림은 서버(Cloud Functions)에서만 발송되므로 클라이언트 권한 설정을 바꿀 필요가 없다
스팸 위험 — 알림이 너무 잦으면 오히려 무시하게 된다. 특히 위 표의 구매 승인 신청 8종은 빈도가 높을 수 있어, 개별 알림 대신 일정 주기로 모아 보내는 다이제스트 방식이 나을 수도 있다 — 실제 신청 빈도를 보고 나서 판단할 열린 문제로 남겨둔다.

웹훅 URL 등록 방식 — 관리 센터 UI로 입력 (절충안)

CLI로 firebase functions:secrets:set을 직접 실행하는 대신, 통합 관리 센터 화면에서 URL을 입력하고 싶다는 요구가 있었다. 저장 위치를 RTDB로 바꾸는 건 추천하지 않는다 — 05번에서 기록했듯 이 시리즈는 RTDB 규칙 동기화 실수가 실제로 있었던 곳이라, .read:false로 잠가도 규칙 파일 관리 실수 하나에 비밀번호급 값이 노출될 위험이 Secret Manager보다 크다. 대신 입력 경로만 UI로 열고 저장은 그대로 Secret Manager로 보내는 절충안을 쓴다.

1) 관리 센터에 "디스코드 웹훅 URL 설정" 입력창 추가 (관리자 전용) 2) 새 함수 setDiscordWebhookUrl({ url })(onCall, 관리자 전용) → RTDB에 쓰지 않는다 → @google-cloud/secret-manager의 addSecretVersion으로 DISCORD_WEBHOOK_URL 시크릿에 새 버전을 추가한다 → 입력값을 그대로 돌려주지 않는다(쓰기 전용) — UI는 "설정됨 / 설정 안 됨" 상태만 표시하고 값 자체는 절대 다시 보여주지 않는다 3) 알림을 실제로 보내는 트리거 함수들은 항상 최신 버전(latest)을 읽으므로 admin-center에서 값을 바꾸면 재배포 없이 바로 다음 알림부터 반영된다
이 함수가 동작하려면 미리 준비돼 있어야 하는 것
  • 시크릿 컨테이너 최초 생성 — DISCORD_WEBHOOK_URL이라는 이름의 시크릿 자체는 CLI로 한 번은 만들어야 한다(firebase functions:secrets:set DISCORD_WEBHOOK_URL --project soop-stock-market, 최초 값은 아무 문자열이나 넣고 이후 UI에서 덮어써도 된다). 함수가 "새 버전 추가"만 하도록 권한을 좁히기 위해, 컨테이너 생성 자체는 사람이 한 번 해두는 편이 안전하다
  • IAM 권한 — admin-center의 Cloud Functions가 쓰는 서비스 계정에 Secret Manager의 "보안 비밀 버전 관리자"(roles/secretmanager.secretVersionManager) 역할을 GCP 콘솔 IAM 페이지에서 부여해야 한다. 프로젝트 공유 IAM을 건드리는 작업이라 콘솔에서 직접 확인하며 하는 걸 권장한다
  • 패키지 추가 — admin-center/functions/package.json에 @google-cloud/secret-manager 의존성 추가(코드 작성 시 같이 처리)
